# The bubble that vanishes out of nowhere (T40)

**Symptom:** every now and then the bubble disappears, but Hear AI keeps working (the hotkey records, the
transcription pastes). Without the bubble you cannot see whether recording started.

**In one sentence:** it was not possible to prove, on this machine, *what* the real cause of the day-to-day disappearance is.
What was proven: (1) four ways for the bubble to vanish that the old code did not recover from, (2) a resting state that was
already almost invisible on a dark background, (3) a "dimmed" resting state that lasted the whole session until the first
dictation. All three were fixed, and the app now **watches itself and writes a log** so the real cause can be
identified the next time it happens.

## 1. Causes tested

Each row was reproduced in an automated test (`tests/test_bubble_watch.py`). "Before" = the v1.2 code,
which only reacted to screen signals (`screenAdded/Removed`, DPI, geometry); there was no watchdog.

| Condition (how the bubble vanishes) | Before (v1.2) | Now |
|---|---|---|
| `hide()` — window hidden | stays hidden (6 s of event loop later) | comes back within ≤ 1 cycle (2 s) |
| Window opacity at 0 | stays hidden | comes back within ≤ 1 cycle |
| Position outside all screens | only comes back if there is a screen signal | comes back within ≤ 1 cycle |
| Lost `WS_EX_TOPMOST` (another window "went in front" forever) | never comes back | comes back within ≤ 1 cycle |
| Qt thinks the window is visible, but Win32 hid it (`IsWindowVisible` = false) | never comes back | comes back within ≤ 1 cycle (`SWP_SHOWWINDOW`) |
| Resting state on a **dark** background | disc 1.0–1.3 : 1 against the background (invisible); only the isotype shows | light rim: edge of 4.2–4.8 : 1 |
| Resting state after loading the model, **before the 1st dictation** | stayed in the "loading" look (isotype at 45% + ring) for the whole session | goes back to the normal resting state as soon as the model loads |

"Before × after" evidence (same scenario, Qt offscreen): without the watchdog the bubble stays at
`isVisible=False, opacity=0, off-screen` 6 s later; with the watchdog it comes back in **2.03 s** (one cycle).
With real Win32 (subprocess, full `QtUi`, `windows` platform, bubble parked off the monitor):
topmost loss recovered in 0.04 s, and the other four in 0.11 s (the test's 100 ms cycle), without activating the
window and without changing the foreground window.

**What was NOT reproduced:** real system events (locking/unlocking the screen, suspend/resume,
restarting Explorer, turning off a monitor, changing Windows scaling). They reach the app as
Windows messages; in the tests those messages were **posted** to the test window and the app recognized them and
reasserted the bubble, but no real event was triggered on the user's PC. If the day-to-day cause is one of
these, the log (section 4) will show it.

## 2. What the watchdog covers

- **Watchdog (every 2 s):** reads the bubble's state (cheap: no repaint, does not wake the 16 ms animation timer;
  0.011 ms per cycle, measured with real Win32 — about 0.0005% of one core) and, if it *should* be
  visible, fixes only what is wrong:
  `show()`, window opacity → 1, reposition (`ensure_bubble_visible`) and reassert topmost with
  `SetWindowPos(HWND_TOPMOST, 0,0,0,0, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE|SWP_SHOWWINDOW)`.
  **It never activates the window nor takes focus from the field you are dictating into** (`WindowDoesNotAcceptFocus`,
  `WA_ShowWithoutActivating` and `SWP_NOACTIVATE` preserved and tested).
- **Windows events** (reasserts ~800 ms later, so the screen settles; several warnings in a row become a single
  reassertion): `WM_DISPLAYCHANGE`, lock/unlock and session connect/disconnect
  (`WTSRegisterSessionNotification` on the bubble window, cancelled on exit), suspend/resume
  (`WM_POWERBROADCAST`) and the registered message `TaskbarCreated` (Explorer restarted).
- **When recording starts (hotkey or any other way):** the bubble is reasserted BEFORE painting "recording".
- **Always-noticeable resting state:** a thin light rim + soft glow around the disc at rest/loading. On a
  light background the disc itself stands out (6.6–11 : 1); on a dark background, the rim. Only at rest: recording and
  transcribing stay as they were. (comparison captures generated by the tests)
  (before | after), regenerable with `PYTHONPATH=src python tests/test_bubble_watch.py`.
- **"Mostrar/recentralizar bolha" item** (Show/recenter bubble) (tray menu and the bubble's right-click menu): reasserts everything. If the saved
  position is still valid, the bubble goes back to it and `bolha.json` is **not touched**; if it is invalid/off
  screen, it goes to the default position on the main screen (the file is not deleted either).
- **Indicators independent of the bubble** (already existed; now tested): the tray icon gets the red dot
  and the tooltip says "gravando" (recording); and the short start (880 Hz) and end (660 Hz) beeps play with `beep` on.
  The option in the Settings window belongs to another task.
- **It respects what you chose:** `bubble_hide_when_idle` on + at rest = hiding is what you asked for, the watchdog
  does not "recover" it. A position over the taskbar is also respected (the watchdog only acts if less than half of the
  bubble is over any screen) and the watchdog does not touch the position while you drag the bubble.

## 3. Known limit

Applications/games in **exclusive full screen** can cover any window, including a `TOPMOST` one. In that case
the watchdog cannot (and should not) force the bubble on top. This case is covered by: the red tray icon and the
start/end beep.

## 4. How to collect the log when it happens

1. As soon as the bubble vanishes (the history keeps about **21 hours**: 192 bytes every 5 s, 3 files of up to
   1 MB), open the tray menu → **Abrir pasta de logs** (Open logs folder).
2. Copy `bolha-diag.log` (and `bolha-diag.log.1`, `.2` if they exist) and keep it together with the approximate time the
   bubble vanished and what you were doing (locked the screen? touched a monitor? opened a full-screen game/video?).

The file only has **states, geometry and events** (never dictated text nor audio; the values go through a
filter that only accepts numbers, 0/1 and short identifiers, and there is a test that looks for dictated text in the log).

How to read it:

```
12:53:26.222 STATE visible=1 native_visible=1 opacity=1.00 frame_opacity=0.85 state=idle hide_when_idle=0 x=278 y=688 visible_on_any=1 screen=\\.\DISPLAY1 topmost=1 z_above=0
12:53:26.667 EVT name=fix reason=vigia actions=topmost native_ok=1 was_visible=1 was_native_visible=1 was_opacity=1.00 was_inside=1 was_topmost=0 state=idle
12:53:27.113 EVT name=display_change
```

- `STATE` (every 5 s): `visible` (Qt thinks it is visible), `native_visible` (Windows thinks so),
  `opacity` (of the window), `frame_opacity` (the painted one; 0.85 at rest), `state`, `x`/`y`,
  `visible_on_any` (it is over some screen), `screen`, `topmost` and `z_above` (how many windows are above it in the
  Z order; a few is normal).
- `EVT name=fix`: a fix that was made. `actions` says what was repaired, `reason` why (`vigia` (watchdog), `recording`,
  `menu` or the Windows event) and the `was_*` fields show what was wrong.
- `EVT name=display_change | session_lock | session_unlock | power_suspend | power_resume | taskbar_created`:
  the Windows event that arrived.

**How to interpret it when the bubble vanished and the log has NO `fix` at that moment:** if the last `STATE` before the
disappearance shows `visible=1 native_visible=1 opacity=1.00 visible_on_any=1 topmost=1`, the window *was in the right
place and opaque*, and something was covering it or Windows did not draw it (exclusive full screen, video/game
overlay, compositor failure). That is exactly the information that was missing.

## 5. Manual test with real events (NOT run in this task)

With Hear AI open and the bubble visible, **one at a time**, and checking whether the bubble stays in view (or comes back
within ~3 s) and what `bolha-diag.log` recorded: Win+L and unlock; suspend and resume; dragging the Explorer window…
and restarting Explorer from Task Manager; connecting/disconnecting a monitor; changing Windows scale
(100% → 125%); opening a full-screen video/game (expected: it may cover it — see section 3).

## 6. Findings outside the scope

- `bubble_hide_when_idle` and `bubble_idle_opacity` exist in `config.json` and in the Settings window, but
  `QtUi` creates the bubble with the default model and **does not pass these values to `BubbleModel`**: the option today has no
  effect on the bubble. I did not touch it (the model and the Settings window are not part of this task); the watchdog already reads
  `hide_when_idle` from the model and will respect it by itself when someone turns the option on.
- The watchdog reads two internal details of the bubble, without changing them: `bubble._dragging` (do not fix the position while
  dragging) and `bubble.model._hide_when_idle`. If the clicks/model task renames these fields, adjust
  `QtUi._dragging` / `QtUi._hide_when_idle`.
- Qt delivers each native message to the filter more than once; that is why there is the ~800 ms grouping and the log
  does not repeat the same event while a reassertion is pending.

## 7. Design decisions

- Watchdog interval 2 s; log sample every 5 s (its own timer, to be exact); event-based reassertion
  with a grouped 800 ms delay.
- "Off screen" for the watchdog = less than 50% of the shape over the **full** screen geometry (including the
  taskbar), looser than `ensure_bubble_visible` (whole shape in the usable area, used on screen
  signals), so the watchdog never "fights" a deliberately chosen position.
- Log: `RotatingFileHandler` 1 MB, 2 backups (3 files), a standalone `logging.Logger` (it does not go to `hear-ai.log`).
- The watchdog log is only created with the bubble on (`show_bubble=True`, the real app); tests that build
  `QtUi` with `show_bubble=False` write nothing to the logs folder.
- Win32 only on the Qt `windows` platform (on `offscreen` the `winId()` is not an HWND and nobody touches it).
